# Implementation Plan: URL Check Onboarding Completion

**Branch**: `[054-url-check-onboarding]` | **Date**: 2026-11-02 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/054-url-check-onboarding/spec.md`

## Summary

Close the URL Check onboarding gaps from the monitoring gap analysis. The new-Component composite flow will accept the same applicable URL Check fields as the regular editor, including API authentication and optional availability target/window. An existing ACTIVE Component with zero ComponentInstances gains a focused manual-instance write (`POST /components/:id/instances`, `component:update`) that saves the first instance without duplicating the Component; the regular URL Check editor then owns check setup. Role-sensitive write fields are enforced, not merely hidden: Credential references require `credential:read` and Import Agent selection requires `agent:read`, while ordinary checks and Hub setup remain EDITOR actions.

No database migration is required. The change reuses `component_instances`, `component_monitoring_setups`, `url_checks`, `credentials`, `import_agents`, and existing audit conventions.

## Implementation Approach

1. **Backend seam**: add `POST /api/v1/components/:id/instances` under `component:update`. The service resolves an ACTIVE component by UUID, rejects existing instances with `409 CONFLICT`, creates a manual `RUNNING` instance with UUID v7, `externalId=manual:<component-slug>`, unique slug per ADR-046, and a `component_instance` `created` audit event inside one transaction.
2. **Payload-level role guards**: ordinary check/setup writes remain EDITOR. A non-null `credentialId` requires `credential:read`; selecting `AGENT` vantage or a non-null `agentId` requires `agent:read`. This applies to the composite route, regular check create/update, and monitoring-setup update using the effective setup after patch.
3. **Frontend sharing**: extract Credential auth fields and target/window controls from the regular URL Check editor into reusable pieces, then wire them into each repeated row of the composite flow. The submit path sends `authMode`, `credentialId`, `authConfig`, `availabilityTarget`, and `targetWindow` using the same validation rules.
4. **Zero-instance UX**: when an authorized user opens URL Checks on a Component with no instances, show a first-instance action. Save through the new endpoint, refresh the component detail, then present the normal URL Check editor. A failed later check setup intentionally keeps the valid first instance.
5. **Contract/docs**: update OpenAPI and generated API docs in the same change; add ADR-125 to ratify the endpoint and role boundary; update URL Check/catalog docs and the roadmap.

## Risks and mitigations

- **Privilege bypass through crafted API payloads**: guard write payloads server-side; tests cover EDITOR denial and ADMIN success.
- **Duplicate or race-created first instances**: service rejects any existing instance and the manual `externalId` remains deterministic; duplicate-key conflicts map to `409 CONFLICT`.
- **Partial composite creation**: existing transaction is preserved; invalid auth/target/setup rolls back Component, instance, setup, and checks.
- **UI/auth parity drift**: extract shared controls and payload/validation helpers; tests cover API-category auth and non-API hiding.
